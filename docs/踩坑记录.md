## 一、板级与硬件

### 1.1 串口读数恒为 4095：PA3 根本不是光敏引脚

- **现象**：ADC 采集程序跑起来了，但串口打印的 `ADC0 = 4095` 恒定满量程，怎么调都不变。
- **根因**：开源工程里 ADC 通道配在 **PA3**，但我这块探索者板上 **PA3 是 USART2_RX（蓝牙串口）**，本机没接蓝牙模块 → 引脚悬空 → 悬空输入被拉满，读到 4095。
  真正的电位器在 **PA5（ADC1_IN5）**，光敏在 **PF7（ADC3_IN5）**。
- **解决**：用 PyMuPDF 解析开发板原理图 PDF，确认真实引脚映射，然后改 `adc.c` 4 处（通道 `ADC_CHANNEL_3 → 5`、GPIO `PIN_3 → 5`、DeInit 引脚、注释）。
- **一句话**：**拿到新板子先读原理图确认引脚复用，别信工程里的默认配置，也别靠经验猜。**

### 1.2 读数卡在 3110（≈2.5V）拧电位器不动：P11 跳线帽插错

改到 PA5 后，数值停在 3110 附近抖动，拧电位器纹丝不动。

- **排查证据链（这套方法值得记）**：
  1. 万用表量电位器三脚：`3.3V / 2.33V / 0V`，拧动后抽头 **2.33V → 3.0V 会变** → **电位器本身是好的**
  2. 矛盾点：源在变、ADC 读数不变 → 说明 **PA5 没接到抽头**
  3. 查 P11 排针（4 脚：RV1 / DAC / ADC / TPAD），跳线帽插的是 **ADC↔TPAD**
- **根因**：P11 是给 PA5 选信号源的跳线，插到 TPAD 后 PA5 接的是触摸按键的固定偏置（约 2.5V），所以读数死卡在中间值。
- **解决**：跳线帽从 `ADC↔TPAD` 改插 `ADC↔RV1`，ADC0 立刻从 4 平滑扫到 4095。
- **一句话**：**「恒满量程」= 悬空/接错，「恒中间值」= 接到了别的信号源——两种异常值对应不同故障类型。**

### 1.3 芯片型号与 Flash 下载算法：算法藏在 `.uvoptx` 里

- **现象**：开源工程默认 STM32F407**VET6**（512KB Flash），我的板子是 **ZGT6**（1MB）。
- **根因**：`Options for Target → Device` 改了型号还不够，**Flash 下载算法不在 `.uvprojx` 里，在 `.uvoptx` 里**。
- **解决**：改 `.uvoptx` 三处：`STM32F4xx_512 → STM32F4xx_1024`、`-FL080000 → -FL100000`、`STM32F407VETx → STM32F407ZGTx`。
- **一句话**：**Keil 工程里 `.uvprojx` 管编译配置，`.uvoptx` 管调试与下载配置，改 Flash 容量要动后者。**

### 1.4 跳线帽丝印是「芯片视角」不是「MCU 视角」

- **现象**：按丝印字面接 —— `RS485_TX` 接 MCU 的 TX、`RS485_RX` 接 MCU 的 RX —— 通信完全不通。
- **根因**：丝印是从 **SP3485 芯片视角**命名的：
  - `RS485_RX` 其实是芯片的 **DI**（芯片"接收"MCU 数据）→ 应接 MCU 的 **TX = PA2**
  - `RS485_TX` 其实是芯片的 **RO**（芯片"发送"给 MCU）→ 应接 MCU 的 **RX = PA3**
  所以正确接法看着像接反了：**PA2 → RS485_RX、PA3 → RS485_TX**。
- **一句话**：**两个设备互联，一方 TX 必接另一方 RX；丝印的 TX/RX 要看清是谁的视角。**

### 1.5 误判方向控制有反相三极管，白折腾半天

- **现象**：一度以为 PG8 到 DE/RE 之间有反相电路，来回对调方向宏和跳线帽，越调越乱。
- **真相**：PG8 **直接连** DE//RE（DE 高有效、RE 低有效，短接后单脚控制），所以就是「高=发送、低=接收」，不需要对调。
- **一句话**：**方向控制先读原理图确认有没有反相器件，别用「对调宏试试看」的穷举法。**

## 二、Modbus / RS485

### 2.1 A/B 接反 → 从站完全静默

- **现象**：发 `01 03 00 00 00 03 05 CB`，从站一个字节都不回。
- **根因**：A/B 接到 USB-485 的 B/A（交叉了）。RS485 靠 A-B 压差表示逻辑（A>B 为 1），接反等于**把整条逻辑取反**，从站收到的帧 CRC 必然错，静默丢弃。
- **解决**：对调成 **A→A、B→B**，立刻有响应。
- **一句话**：**RS485「发出去没回应」，第一件事是对调 A/B——成本 5 秒，命中率极高。**

### 2.2 波特率明明是 115200，实际必须用 9600

- **现象**：CubeMX 里 USART2 配的 115200，但主站必须设 9600 才能通信。
- **根因**：`Modbus_Init()` 会加载 Flash 里存的配置（默认 `DEFAULT_BAUD_RATE = 9600`）并**重新调用 `HAL_UART_Init()` 覆盖**掉 CubeMX 的设置。
- **一句话**：**外设初始化和协议栈初始化谁后跑谁生效——`Modbus_Init` 在 `MX_USART2_UART_Init` 之后，所以它说了算。**

### 2.3 GND 接错，比不接更糟

- **现象**：把 GND 接到相邻信号脚，主站彻底收不到数据。
- **真相**：桌面短距离、两边都 USB 供电时其实**不需要额外接 GND**；多接一根接错的 GND 会把差分拉偏。
- **一句话**：**差分信号的优势就是不依赖严格共地；要共地也要接对位置，接错反而引入故障。**

### 2.4 串口助手勾了「发送新行」，8 字节帧变 10 字节

- **现象**：串口助手发 `01 03 00 00 00 01 84 0A`，从站无响应。
- **排查**：在 `HAL_UARTEx_RxEventCallback` 里临时加一行「打印收到几个字节」，发现收到的是 **10 字节**而不是 8。
- **根因**：XCOM 勾选「发送新行」会自动在末尾追加 `\r\n`（0x0D 0x0A）。Modbus RTU 帧长严格固定，多 2 字节 CRC 就对不上。
- **一句话**：**Modbus 是纯二进制协议，末尾绝不能带回车换行；「回显收到字节数」是定位收不到响应的最快手段。**

### 2.5 漏写接收回调，从站一个帧都收不到

- **现象**：配置、地址、CRC 全对，从站仍然不响应。
- **根因**：协议栈靠空闲中断接收，必须在 `main.c` 的 `USER CODE BEGIN 4` 里实现：
  ```c
  void HAL_UARTEx_RxEventCallback(UART_HandleTypeDef *huart, uint16_t Size)
  {
      Modbus_RxCpltCallback(huart, Size);
  }
  ```
  漏了它 = 协议栈永远拿不到数据。
- **一句话**：**用开源协议栈时，先确认它要求的回调/钩子函数是否全部注册，缺一个就是"完全不工作"。**

### 2.6 沿用了 F103 的 Flash 地址，差点擦掉自己的程序

- **现象**：协议栈默认 `MODBUS_FLASH_ADDR = 0x0800F800`，用于存从站地址/波特率。
- **根因**：这是 **F103** 的默认值；在 F407ZGT6 上该地址落在程序区，写配置会**擦掉用户程序**。
- **解决**：改成 `0x080E0000`（F407ZGT6 最后一个扇区，扇区 11，128KB），与协议栈硬编码的 `FLASH_SECTOR_11` 匹配。
- **一句话**：**移植带 Flash 存储的协议栈，第一件事是核对存储地址与芯片扇区划分。**

### 2.7 `huart1` 写成 `USART1`，一次报 10 个错

- **现象**：`modbus_config.h(20)` 和 `main.c(168)` 共 10 个 error。
- **根因**：两个完全不同的东西：

| 标识符 | 是什么 | 定义在哪 |
|---|---|---|
| `huart1`（小写） | 串口**句柄变量**，类型 `UART_HandleTypeDef` | CubeMX 生成在 `main.c` |
| `USART1`（大写） | 外设**基地址宏**，类型 `USART_TypeDef *` | 芯片头文件 |

写 `extern UART_HandleTypeDef USART1;` 会让宏展开成非法语法，还污染 `main.c` 里的 `huart1.Instance = USART1;`，产生连锁报错。
- **一句话**：**HAL 里「句柄」和「外设寄存器宏」是两层东西，混淆一次能带出一串无关错误。**

### 2.8 代码写在 `while(1)` 外面

- **现象**：`warning: statement is unreachable`，`mb_holding_regs[0] = 12345;` 永不执行。
- **根因**：代码落在无限循环的 `}` 之后。
- **一句话**：**CubeMX 工程里用户代码必须写在 `USER CODE BEGIN/END` 区内，位置错了会静默失效。**

## 三、FreeRTOS

### 3.1 看门狗一旦启动就停不下来，调试下断点必复位

- **现象**：ST-Link 单步调试时，程序会"莫名其妙重启"。
- **根因**：IWDG 启动后**无法软件停止**，断点停住时计数器继续走，超过 2.5s 直接复位 MCU。
- **解决**：调试阶段不启动看门狗；正式运行直接烧录，不在看门狗这段下断点。
- **一句话**：**IWDG 的"独立性"是优点也是调试障碍——它不依赖系统时钟，所以 CPU 停住它照走。**

### 3.2 滤波窗口初值为 0，开机数据从 0 往上爬

- **现象**：上电后前几秒读数偏低，慢慢才逼近真值。
- **根因**：滤波缓冲区初始化为 0，前 N 次输出混着 0。
- **解决**：`Filter_Init()` 用**第一次采样的真实值填满整个窗口**，上电即正确。
- **一句话**：**数字滤波器要考虑启动瞬态，用首次采样值预热窗口是标准做法。**

### 3.3 CubeMX 重新生成，把之前的手动配置全部冲掉

- **现象**：勾选 FreeRTOS 重新生成代码后，ADC 的 DMA 连续请求、EOC 选择、温度通道采样时间、ADC3 连续转换全部回退；`hal_conf.h` 里 `HAL_SRAM_MODULE_ENABLED` 被注释 → LCD 依赖的 FSMC/SRAM 未定义 → **18 个编译错误**。
- **解决**：对照备份逐项恢复，重新使能 SRAM 模块。
- **一句话**：**CubeMX 只保证"生成它的配置"，任何在生成代码里手改的东西都会被覆盖——改完必须对照 checklist 复查。**

### 3.4 持锁睡眠：`osDelay` 写在了锁里面

- **现象**：加了互斥锁后，其他任务响应变慢。
- **根因**：`osDelay` 写在 `osMutexRelease` 之前，任务拿着锁睡觉，别的任务全被堵在门外。
- **解决**：锁只包住访问共享资源的几行，`osDelay` 一律放锁外面。
- **一句话**：**临界区要短到极致——锁里只做数据访问，任何等待/延时都必须放锁外。**

### 3.5 优先级是「数值越大越高」

- **反直觉点**：`osPriorityRealtime = 48` 最高，`osPriorityIdle = 1` 最低。本项目：Modbus(32) > 采集(24) = 点灯(24) > 显示(8) = 喂狗(8)。
- **一句话**：**Modbus 能及时响应靠两件事：优先级最高 + 允许抢占，缺一不可。**

### 3.6 `osKernelStart()` 之后的 `while(1)` 是死代码

- **根因**：调度器启动后永不返回，`main` 里的 `while(1)` 永远不执行。迁移时容易留着旧代码，误以为还在跑。
- **一句话**：**迁移到 RTOS 后要把原 `while(1)` 的代码搬进任务并删除，否则会出现"改了没生效"的假象。**

## 四、日志 / FATFS / EEPROM

### 4.1 `printf` 没重定向 + 没勾 MicroLIB，串口一片空白

- **现象**：日志代码写了，串口什么都没有。
- **根因**：两个前置都没做 —— Keil 没勾 **Use MicroLIB**，也没实现 `fputc`。
- **解决**：
  ```c
  int fputc(int ch, FILE *f)
  {
      HAL_UART_Transmit(&huart1, (uint8_t *)&ch, 1, 0xFFFF);
      return ch;
  }
  ```
  注意 `fputc` 要 `return ch`（字符本身），不能写成 `return HAL_UART_Transmit(...)`（那是状态码）。
- **一句话**：**调试串口 USART1 与 Modbus 的 USART2 要分清；`printf` 重定向是"看不见输出"的头号原因。**

### 4.2 include 路径自我叠加

- **现象**：`log.c` 里写 `#include "Core/BSP/LOG/log.h"` 报 `cannot open source input file`。
- **根因**：双引号先找**当前文件所在目录**，再拼上写的路径 → 变成 `Core/BSP/LOG/Core/BSP/LOG/log.h`。
- **一句话**：**同目录头文件直接 `"log.h"`；双引号会以当前目录为基准拼接相对路径。**

### 4.3 声明与实现函数名不一致 / 枚举顺序反了

- **现象①**：链接报 `Undefined symbol`（`log.h` 声明 `log_print`，`log.c` 实现 `log_output`）。
- **现象②**：等级过滤方向反了（枚举写成 `ERROR=0 ... DEBUG=3`，门槛判断变成"只打印更严重的"之外的全放行）。
- **一句话**：**日志库这种"小而对称"的代码，最容易出错的地方就是名字成对性和枚举方向。**

### 4.4 日志轮转顺序错，FATFS 返回 `FR_LOCKED`

- **根因**：文件还开着时不能改名。顺序必须是 **① `f_close` → ② `f_rename` → ③ 新建**。
- **补充**：只保留两份（先 `f_unlink` 旧的 `log_old.txt` 再改名），避免无限占用空间。
- **一句话**：**FATFS 的 `f_close` 干两件事：flush 缓冲 + 释放文件句柄；没关就改名一定失败。**

### 4.5 SD 卡写入阻塞了 Modbus 响应

- **现象**：加日志落盘后，Modbus 偶发超时。
- **根因**：SD 卡是**块设备**，写一个字节要"读整块 512B → 改 → 写回 → sync"，比串口（流设备）慢几个数量级，直接在业务任务里写就把任务卡住了。
- **解决**：生产者-消费者——`log_output` 只把格式化好的消息丢进队列立刻返回，由独立的 `LogTask` 去写盘；**队列满时直接丢弃这条日志**（`osMessageQueuePut` 超时传 0），用"突发丢几条日志"换"系统永不卡顿"。
- **一句话**：**块设备与流设备的本质差异，决定了日志必须异步写；实时性优先时要敢于丢日志。**

## 五、树莓派与 Linux 部署

### 5.1 flask-socketio 5.6 默认禁用 Werkzeug，nohup 一跑就 `Exit 1`

- **现象**：`RuntimeError: The Werkzeug web server is not designed to run in production. Pass allow_unsafe_werkzeug=True ...`
- **根因**：新版 flask-socketio 加了安全检查；前台跑能侥幸通过，后台跑必触发。
- **解决**：`socketio.run(app, host='0.0.0.0', port=5000, allow_unsafe_werkzeug=True)`。
- **一句话**：**Werkzeug 是开发服务器，生产要换 gunicorn/eventlet；这个参数是"我确实在演示环境用"。**

### 5.2 systemd 的 `ExecStart` 里不能写 `nohup` 或 `&`

- **根因**：systemd 本身就负责守护进程，它期望 `ExecStart` 跑一个**前台**程序；加了 `&` 会让 systemd 以为服务"已退出"，反复重启。
- **一句话**：**systemd 的守护逻辑与 nohup 是重复的，两者叠加反而失效。`enable` 是登记开机自启，`start` 是现在就启动，两件事。**

### 5.3 cpolar 没做 authtoken 认证，隧道永远 `connecting`

- **根因**：没认证，服务端不知道你属于哪个账号，隧道建不起来。
- **解决**：`cpolar authtoken <token>` → 显示 `Authentication successful` → 状态转 `online`。
- **一句话**：**隧道地址不会写在 `error.log` 里（那是空的正说明没报错），要去 dashboard 的在线隧道列表看。**

### 5.4 改 YAML 配置的三连环坑（折腾最久的一次）

- **坑①**：`nano` 里 `Ctrl+K` 删行删过头，把 `addr` 行删掉了。
- **坑②**：`cat << 'EOF'` 粘贴时每行带了前导空格，结束符 `EOF` 没顶格 → shell 一直等输入（提示符变 `>`）。
- **坑③**：单行 `printf` 太长被终端折行，`addr: "5000"` 被拆成两行，YAML 解析失败。
- **解决**：改用短命令 + 每次改完立刻 `cat` 验证；最后用一条 `sed` 修复折行。
- **一句话**：**YAML 对缩进和 TAB 敏感；在 Linux 上改配置文件，「短命令 + 立即回读」比一次性贴长文本可靠。**

### 5.5 手机热点 IP 变了 → SSH 连不上；直连网线也不行

- **根因①**：手机热点的网段会周期性变化，树莓派 DHCP 拿到的地址跟着变，手里的旧 IP 失效。
- **根因②**：**新版 Raspberry Pi OS（Bookworm / NetworkManager）在"网线没有 DHCP 服务器"时不会自动分配 169.254 link-local 地址**；而 Windows 那边会自动编一个，于是"笔记本有地址、树莓派没地址"，永远连不上。
- **解决**：重开热点让树莓派走 WiFi 自动连回；用 `arp -a` 按 MAC 前缀 `b8:27:eb` 找出树莓派新 IP。
- **一句话**：**老系统（dhcpcd）和新系统（NetworkManager）的 link-local 行为不同，直连不通先别怀疑硬件。**

### 5.6 终端能 SSH，VS Code 连不上

- **根因**：`~/.ssh/config` 里只有旧 IP 且带 `User ljw`；新 IP 没写进去，VS Code 就用 Windows 用户名 `lenovo` 去连，树莓派上没这个用户 → 认证失败。终端能连是因为手动敲了 `ljw@`。
- **解决**：config 里给目标 IP 补 `User ljw`，并加一个固定别名 `Host pi`。
- **一句话**：**"终端通、VS Code 不通"几乎都是 SSH config 缺 `User`，不是网络问题。**

## 附：这套排障方法论的通用三步

1. **先分层定位**：网络/协议/驱动/应用，一层层往下切，别一上来就改代码。
2. **先取证再动手**：串口打字节数、万用表量电压、`arp -a` 找 MAC、`cat` 回读配置——**先拿到"事实"，再猜"原因"**。
3. **改一个变量就验一次**：A/B 对调就立刻发帧、改跳线帽就立刻看读数，避免一次改多处导致新问题掩盖老问题。
