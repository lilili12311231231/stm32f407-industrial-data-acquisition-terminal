## 二、三个转折点（复盘时最值得讲）

### ① 09-10：从"跑 demo"到"能定位问题"

阶段 1 花了整整一天，5 个坑里有 4 个**不在代码里**——是引脚认错、跳线帽插错、Flash 算法选错。
转折点是学会了**用万用表三步定位**：量源供电 → 量源输出是否随输入变化 → 量目标引脚是否跟随。
这一步之后，"读数不对"不再是玄学，而是一条可以逐段排除的链路。

### ② 09-13：物理层升级让我理解了"分层"

把 Modbus 从 TTL 换成 RS485，**协议源码一行没改**，只改了 4 处配置。
同一套 `modbus_slave.c` 在 TTL 上跑、在 485 上也跑，主站从 Windows 换成树莓派照样跑。
——这就是"物理层与协议层解耦"的实感，比背书上的 OSI 七层有用得多。

### ③ 09-15：从"能跑"到"能扩展"

裸机 `while(1)` + `HAL_Delay(100)` 的问题不是跑不动，而是**所有事被绑死在一个节奏里**。
迁移到 5 个任务之后，采集、显示、Modbus、喂狗各自按自己的周期跑，Modbus 靠"高优先级 + 抢占"保证及时响应。
这是这个项目里唯一一次"重构"，也是最像工程实践的一次。

## 三、工程习惯（附带的收获）

| 习惯 | 具体做法 |
|---|---|
| 阶段留快照 | 每完成一个阶段复制整个工程目录并标注状态（`裸机备份_20260914`、`阶段3快照-已验证`），改坏了能立刻回退 |
| 一阶段一存档 | 每个阶段写一份 `存档.md`：目标 / 验收项 / 关键代码 / 踩坑 / 遗留，共 16 份 |
| 只改配置不改源码 | 用第三方协议栈时坚持"源码零改动"，所有适配集中在 `config.h`，升级库不用重新适配 |
| 用户代码区纪律 | 严格写在 CubeMX 的 `USER CODE BEGIN/END` 之间，重新生成不丢代码 |
| 先取证再动手 | 串口打字节数、万用表量电压、`arp -a` 找 MAC、改完配置立刻 `cat` 回读 |

## 四、如果重做一遍会改什么

1. **一开始就用 Git 分阶段提交**，而不是做完再一次性上传——提交历史本身就是最好的开发记录。
2. **提前写 `docs/`**，把调试存档和代码放在同一个仓库里，避免"代码在仓库、过程在本地"的割裂。
3. **给看门狗和 Flash 存储留测试开关**，破坏性验证（复位、擦写）能一键跑，不用手改代码。
4. **早一点做长稳测试**，稳定性问题越晚发现，排查成本越高。
